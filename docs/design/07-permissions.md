# 07 — نموذج الصلاحيات والموافقات | Permissions

> Idexal — Agentic IDE. مرجع: [index](README.md) · [الإعدادات](03-settings.md)

## المبدأ

نموذج أمان **طبقي** بالثقة التصاعدية: الوكيل يبدأ قراءةً بحرية، ويكتسب حق الكتابة
والأوامر وفق ما يسمح به المستخدم. القرار النهائي دائمًا للمستخدم، والحدود تُفرض
في النواة لا في الواجهة (حتى لو استُدعيت النواة من طرفية فقط).

├───────────────────────────────────────────────────────────────┤
│ الطبقة 2: صلاحيات الأدوات (قابلة للضبط من صفحة الإعدادات)        │

├───────────────────────────────────────────────────────────────┤
│ الطبقة 1: نية التشغيل (في الغلاف)                                │
│   وضع عادي / read-only / موافقة لكل أمر خطير                    │
└───────────────────────────────────────────────────────────────┘

## 1) أمان مسارات النظام (إلزامي دائمًا)

- كل أداة ملفات تستقبل مسارًا **نسبيًا** وتُحلّه داخل الجذر.
- الفحص **واحد** في `tools.rs::resolve_inside_root` يطبّق:
  - تحويل المسارين (الجذر والمرشّح) إلى صيغة canonical (أفضل جهد، يتحمّل مسارات
    غير موجودة بعد للكتابة).
  - مقارنة بالحدود: `abs == root || abs.starts_with(root + separator)`.
- **حصار بادئة الأشقاء**: `../proj-evil/x` لا يمر تحت جذر اسمه `proj` فقط لأن
  السلسلة تبدأ بـ "proj". (اختبار `sibling_prefix_bypass_is_blocked` يحرسه.)
- نفس الفحص في الغلاف (`app/src/main/workspace.ts`) لقراءة/كتابة التبويبات — الطبقتان
  مستقلتان: حتى لو فشلت إحداهما تبقى الأخرى.

## 2) صلاحيات الأدوات (من صفحة الإعدادات)

| الأداة | الافتراضي | أوضاع | المعنى |
|--------|-----------|-------|--------|
| `read_file` | تلقائي | تلقائي/موافقة/محظور | قراءة أي ملف نصي |
| `list_dir` | تلقائي | تلقائي/موافقة/محظور | سرد المجلدات |
| `write_file` | يتطلب موافقة | تلقائي/موافقة/محظور | كتابة/إنشاء ملفات |
| `run_command` | يتطلب موافقة | تلقائي/موافقة/محظور | تنفيذ أوامر shell |

- الوضع **تلقائي**: يُنفَّذ مباشرة ويُبث الحدث للواجهة (لا يُسأل).
- الوضع **يتطلب موافقة**: تُعلَّق الجولة، تُعرض البطاقة (الأداة، المسار/الأمر،
  وسيطة كاملة) بزري **قبول/رفض**، ثم تُستأنف.
- الوضع **محظور**: يعيد النواة خطأ فورًا بلا سؤال.
- `--read-only` (مراجعات/تحليلات): يجبر الأدوات على المجموعة الفرعية read/list — بلا
  كتابة وبلا أوامر، مهما قال النموذج.

### blocklist الأوامر (من صفحة الإعدادات)

قائمة أنماط (regex) تُفحص قبل تنفيذ أي أمر؛ المطابق يُرفض فورًا:
`git push`, `rm -rf`, `sudo`, `npm publish`, `DROP TABLE`… (قابلة للتوسيع).

## 3) نية التشغيل (في الغلاف)

- الواجهة تعرض حالة "صلاحيات" شفافة: شارة `local · no account` + تلوين ألوان
  أحداث الأدوات (نجاح/فشل/موافقة معلّقة).
- مهام الوكيل تعمل في **مجلد المستخدم المفتوح** (cwd = workspace root) — النواة
  لا تُشغَّل من مجلد بدء التشغيل العشوائي.
- أوامر Git التعديلية (إضافة/إيداع/سحب) غير موجودة حتى يُبنى تأكيد صريح في الواجهة —
  "إعادة كتابة مستودع المستخدم بصمت غير مقبولة".

## 4) حدود الإخراج (الحماية من الإغراق)

- مخرجات الأدوات تُقصّ إلى 20,000 حرف (مع وسم `… [truncated N chars]`).
- ما يُبث للواجهة يُختصر أكثر (300 حرف) — النموذج يرى الكامل المقصوص، الشاشة ترى الملخص.

## 5) أمان الواجهة (Electron)

- `contextIsolation: true`, `nodeIntegration: false`, جسر `preload` صريح فقط.
- كل وصول للأقراص من main عبر IPC مسمّى — لا IPC عشوائي.
- الفروق وأحداث الوكيل تُرسم عبر DOM nodes (لا innerHTML) — منع حقن المحتوى.
- `webviewTag` مفعّل للمعاينة الحية فقط.

## المصفوفة الكاملة (جدول الصلاحيات)

| الإجراء | مسار القرار | أين يُفرض |
|---------|-------------|-----------|
| قراءة/سرد داخل الجذر | تلقائي (قابل للضبط) | tools.rs + workspace.ts |
| الكتابة | موافقة/تلقائي حسب الإعداد | tools.rs (+ رفض خارج الجذر) |
| الأوامر | موافقة/تلقائي + blocklist | tools.rs + blocklist |
| Git تعديلي | غير متاح حتى UI تأكيد | الغلاف |
| خارج الجذر | **محظور دائمًا** | الفحص الحدودي |

## قواعد الصيانة

1. أي أداة جديدة: تُضاف لـ `definitions()` + `dispatch()` + جدول الصلاحيات هنا.
2. أي مسار: يمر عبر `resolve_inside_root` — لا استثناءات.
3. أي تسهيل مستقبلي ("وضع الثقة الكاملة") يبقى **مغلقًا افتراضيًا**.
